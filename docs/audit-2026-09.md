## 1. Architecture Overview

**Stack:** Next.js 16.3.0 (App Router, Turbopack), React 19.2.8, TypeScript 5 (strict), Supabase (Postgres + Auth + Storage), Tailwind v4, deployed to Vercel. No API backend outside Supabase — the browser/server talk to Postgres directly through PostgREST, gated by Row Level Security. This is a fully "Supabase-first" architecture: **RLS is the security boundary**, not application code. That single fact governs almost every finding in this report.

### Route tree (`src/app/`)

```
/                                    dashboard (stats + recent matters/deadlines)
/login, /signup, /welcome            auth entry points
/auth/confirm                        route.ts — OTP-link landing (the one API route in the app)
/auth/switch-account                 "you're signed in as someone else" prompt
/clients, /clients/new, /clients/[id], /clients/[id]/edit
/matters, /matters/new, /matters/[id], /matters/[id]/edit
/matters/[id]/timeline/new, /matters/[id]/timeline/[eventId]/edit
/deadlines, /deadlines/new, /deadlines/[id]/edit
/documents, /documents/new, /documents/[id], /documents/[id]/edit
/settings                            team roster + invite + (new) Team & Access counts
```

Every feature area follows the *same* shape: `page.tsx` (list), `[id]/page.tsx` (detail), `[id]/edit/page.tsx`, `new/page.tsx`, `actions.ts` (Server Actions). This consistency is real and load-bearing — see §9/§15.

There is exactly **one** API route handler in the whole app (`src/app/auth/confirm/route.ts`); everything else is a Server Action invoked from a `<form action={...}>`.

### Database tables

| Table | Purpose | RLS enabled |
|---|---|---|
| `firms` | Tenant root | Yes |
| `users` | App-level profile, `firm_id` + `role` (`owner`/`member`) | Yes |
| `clients` | Firm's clients | Yes |
| `matters` | Legal matters/cases, belongs to a client + firm | Yes |
| `matter_assignments` | New (this session) — ACL of who can see which matter | Yes |
| `deadlines` | Belongs to a matter | Yes |
| `documents` | Belongs to a matter; file metadata + `storage_path` | Yes |
| `timeline_events` | Belongs to a matter | Yes |

Relationships: `users.firm_id → firms`, `clients.firm_id → firms`, `matters.firm_id → firms`, `matters.client_id → clients`, `deadlines/documents/timeline_events.matter_id → matters` (all `ON DELETE CASCADE`), `matter_assignments.(matter_id, user_id)` unique, both FKs cascade.

### Auth mechanism

Supabase Auth (email/password + email-OTP for invites), session held in cookies via `@supabase/ssr`, refreshed on every request by `src/proxy.ts` → `src/utils/supabase/middleware.ts`. Authorization is **not** role-based-access-control in application code — it's enforced by Postgres RLS policies keyed off `auth.uid()`, via two `SECURITY DEFINER` helper functions: `get_my_firm_id()` (pre-existing, **untracked**, see §4) and `get_my_role()` / `user_can_access_matter()` (added in `0011`).

### Storage

One bucket, `documents`, created **private** (`public: false`) in `0004_documents_dev_policy.sql`. Files are stored at `<matter_id>/<timestamp>-<filename>`. Access is gated by a `storage.objects` RLS policy that parses the matter id back out of the path and re-checks `user_can_access_matter()` — meaning even a leaked/guessed storage path is still access-controlled, not just the app UI. **[Verified live]** the bucket rejects unauthenticated public fetches with `404 Bucket not found` (see §5).

### Environment variables

| Variable | Exposed to browser | Used in |
|---|---|---|
| `NEXT_PUBLIC_SUPABASE_URL` | Yes | `server.ts`, `client.ts`, `admin.ts`, `middleware.ts` |
| `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY` | Yes (this is the anon key, meant to be public) | `server.ts`, `client.ts`, `middleware.ts` |
| `SUPABASE_SECRET_KEY` (falls back to `SUPABASE_SERVICE_ROLE_KEY`) | **No** — server-only | `admin.ts` only |

`admin.ts`'s service-role client (`createAdminClient()`) is called from exactly **one** place in the entire codebase: `src/app/settings/actions.ts`'s `inviteTeammate`, and only after that action re-verifies server-side that the caller's own `users` row has `role === 'owner'`. **[Reviewed statically only]** — confirmed via grep across all of `src/`, no other call sites, no import from any client component.

### 2. Team invites (`/settings` invite form → `/auth/confirm` → `/welcome` / `/auth/switch-account`)
- **Files:** `src/app/settings/{page,actions,InviteForm}.tsx`, `src/app/auth/confirm/route.ts`, `src/app/auth/switch-account/{page,actions}.tsx`, `src/app/welcome/{page,actions}.tsx`, migration `0010_team_invites.sql`.
- **Data flow:** owner submits an email → `inviteTeammate` re-verifies caller is `role: 'owner'` server-side → service-role `admin.auth.admin.inviteUserByEmail` sends the email → `admin.auth.admin.updateUserById` stamps `app_metadata.invited_firm_id`/`invited_role` (only settable via the service-role Admin API, never by the invitee themselves) → invitee clicks the emailed link → `/auth/confirm` verifies the OTP → `ensureUserProfile` reads `app_metadata.invited_firm_id` to create the `users` row in the *correct* firm, matched by the `0010` RLS policy which independently re-checks the same `app_metadata` claim.

## 4. Postgres RLS Audit

### The tenant-isolation model, in plain English

Every tenant-scoped table has a `firm_id` column (or reaches one through `matter_id → matters.firm_id`). A SQL function, `get_my_firm_id()`, looks up the *caller's own* `firm_id` from their `users` row (bypassing `users`' own RLS via `SECURITY DEFINER`, which is necessary to avoid infinite recursion — you can't check a policy on `users` by querying `users` under RLS). Every policy on every tenant table then requires `firm_id = get_my_firm_id()`. Since `auth.uid()` is NULL for an unauthenticated request, `get_my_firm_id()` returns NULL for them, and `firm_id = NULL` is never true in SQL — so an anonymous request sees nothing, by construction, not by an explicit "if not logged in, deny" branch. **This is why firm B can never see firm A's data**: not because the app checks it, but because no policy can ever evaluate to true for a mismatched or absent identity.

On top of firm scoping, as of `0011`, `matters` (and everything under a matter — `deadlines`, `documents`, `timeline_events`, and matter-scoped Storage objects) adds a second layer: `get_my_role() = 'owner'` (sees everything in the firm) **or** an explicit row in `matter_assignments` for that specific matter and user. Both `get_my_role()` and the `user_can_access_matter()` helper are `SECURITY DEFINER` for the same recursion-avoidance reason.

### Policy-by-policy (tracked migrations, verbatim)

I read all 11 migration files in full. Rather than repeat every clause here, the key structural facts:

- **`0001`–`0006`**: dev-only, fully open `USING (true)`/`WITH CHECK (true)` policies granted **to `anon`**, on `matters`, `clients`, `deadlines`, `documents`, plus the `documents` Storage bucket. Explicitly labeled dev-only in their own comments.
- **`0007_restore_firm_scoped_rls.sql`**: drops all of the above anon-open policies. Its own comment states the firm-scoped replacement policies it's "restoring" **were never created by any migration in this repo** — they predate tracked history, created directly via the Supabase dashboard/SQL editor. Same for `get_my_firm_id()` itself. `0007` also documents one confirmed instance of live drift: a Storage policy it expected to find was renamed manually in the dashboard at some point and no longer matches what `0004` created.
- **`0008`**: adds `timeline_events`, again with a dev-only fully-open anon policy (explicitly because of a documented Supabase JWT/PostgREST bug blocking authenticated RLS testing at the time).
- **`0009`**: closes that gap with a firm-scoped policy, `USING (matter_id in (select id from matters where firm_id = get_my_firm_id()))`.
- **`0010`**: adds the invite-acceptance INSERT policy on `users`, checked against `auth.jwt() -> 'app_metadata' ->> 'invited_firm_id'` — correctly unforgeable by the invitee themselves (§2, feature 2).
- **`0011`**: the per-matter-permissions work — full policy set audited in §3's table above; every clause read directly, not paraphrased from a summary.

### Critical finding: the security model's source of truth was split — CLOSED (see Addendum)

**Originally reported as:** `get_my_firm_id()`, plus the original firm-scoped policies for `clients`/`matters`/`deadlines`/`documents`, plus an event trigger originally (and, per the Addendum, incorrectly) referred to as `rls_auto_enable`, all existing only live.

**Independently re-verified against the migration files directly, across three rounds (see Addendum for the full trace):** `matters`, `deadlines`, and `documents` were cleared first — their pre-existing untracked policies were dropped and replaced by tracked, readable policies in `0011` (`drop policy if exists "Users can manage their firm's matters/deadlines/documents"` followed immediately by new `create policy` statements, all in that one file). That left four objects that were actually both untracked and live:
- `get_my_firm_id()` — the single function every tenant-isolation policy in this app depends on. Confirmed via grep: called throughout `0007`/`0009`/`0010`/`0011`, defined (`create function`) nowhere.

## 7. Error Handling & Information Disclosure

Every Server Action in the app follows `if (error) throw new Error(error.message)` (or returns `{ error: error.message }` for the `useActionState` forms). This means a raw Postgres/PostgREST error string — constraint names, column names, occasionally the shape of a query — can reach the browser. Concretely, this is **not** a secrets leak (no credentials, tokens, or env vars are ever in these messages), but it is inconsistent with treating internal schema details as private, and it means users can occasionally see a confusing raw database message instead of a curated one (e.g., a foreign-key violation reading as a raw Postgres error rather than "this record is still in use"). No instance of a stack trace, environment variable, or authentication secret being surfaced was found anywhere in `src/`. **[Reviewed statically only]**.

No errors are silently swallowed in a way that would hide a real failure from the user — every failure path either throws (which Next.js surfaces as an error boundary) or returns a visible `{error}` state. The opposite problem (no debugging signal at all) also doesn't apply: there is no server-side logging of these errors anywhere (no `console.error`, confirmed by grep), which means production failures leave no trace for the developer either — only the end user sees them, once, in the moment.

### Recommended audit/review cadence going forward

Decided, not offered as options: a full audit like this one does not scale to "every feature" or even "every 3-5 features" — most features never touch the trust boundary, and running all 16 sections against them wastes effort and trains everyone to skim the report. Instead:

1. **Every feature, lightweight:** before commit, a two-minute self-check — does this feature read/write data scoped by firm or matter, does it add a new Server Action or API route, does it touch auth/session/storage? A "no" to all three needs nothing beyond the existing lint/typecheck/test gates. This is nearly free, and it's the trigger for step 2.
2. **Trust-boundary-triggered targeted review, same day as the feature:** any "yes" above gets a focused review of only the new surface — new RLS policies get a pgTAP test in the same commit, not deferred; new Server Actions get checked against the existing error-handling/validation patterns. This is where nearly all real risk actually gets caught, continuously, rather than in batches.
3. **Full audit at phase boundaries and high-stakes milestones**, not a feature count: end of a roadmap phase, before onboarding a real paying customer, before handling anything meaningfully more sensitive than what's in the app today (e.g., before payment processing or trust accounting in Phase 5), or after a long stretch without one. A raw "every 10 features" counter treats a settings-page tweak the same as a new integration with an external AI API handling client-confidential case data — the trigger should be risk introduced, not features shipped.

Concretely: the AI case summarization + timeline builder feature that's next introduces a new trust boundary (client-confidential case data leaving the app to a third-party API) and a new non-Supabase dependency, so it gets a targeted review of its own — new API key handling, the new data-egress path, and the "AI-drafted, human-must-accept" guardrail from the strategy doc — before it ships, not deferred to some future full audit.
